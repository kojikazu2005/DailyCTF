# Poly_MAC2 Notes（実際の試行錯誤を反映した版）

## 学び・気づき
- Poly1305 は「内部値 h が 130bit なのに、タグは 128bitしか公開されない」ため、逆算時には上位 2bit を総当たりする必要がある。
- clamp 前の r_raw は情報が失われているため復元不可能。逆算できるのは clamp 後の r のみ。
- PyCryptodome の Poly1305_MAC は、ブロック末尾に付ける “1” の位置が **メッセージ長に依存する**（`1 << (8 * len(msg))`）。
- cryptography の Poly1305 と PyCryptodome の Poly1305_MAC は内部仕様が異なるため、同じ r, s, message を渡しても同じタグにならない。
- 実装依存の細かい仕様を正しく合わせないと、逆算は絶対に噛み合わない。

---

## 試行錯誤ログ
- 最初は「逆算式は正しいはずなのに tag が一致しない」状態が続いた。
- clamp の扱いを疑い、big/little のエンディアンを何度も修正したが一致しなかった。
- carry（上位 2bit）の総当たりも正しいのに、4 つ全部外れた。
- cryptography の Poly1305 を import しているせいで混乱し、「実装が違うのでは？」と疑い始めた。
- PyCryptodome のソース `poly1305.py` を直接読むことにした。
- そこで `n += 1 << (8 * len(block))` を発見し、  
  **「message が 1 バイトなら足すべき値は 2^8、16 バイトなら 2^128」**  
 という仕様差分に気づいた。
- 自分の逆算式は常に `m + 2^128` を使っていたため、計算している h が完全に別物になっていた。
- この仕様に合わせて逆算式を修正したところ、ようやくタグが一致した。

---

## まとめ
今回の最大の学びは「暗号の逆算は、実装の細部を 1bit も間違えずに合わせないと絶対に噛み合わない」ということ。  
Poly1305 のような MAC は特に実装依存の差分が多く、RFC の式だけでは不十分であることを痛感した。
